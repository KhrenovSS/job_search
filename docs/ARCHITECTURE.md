# Архитектура HH-Scout

## Компоненты
```
┌──────────────────────────── Debian-хост, X11-сессия владельца (24/7) ────────────────────────────┐
│ Firefox ESR --marionette (127.0.0.1:2828, логин владельца на hh.ru)                              │
│        ▲ Marionette (одна сессия!)                                                                │
│ geckodriver --connect-existing  ← дочерний процесс на время серии, потом убивается (без quit())    │
│        ▲ WebDriver                                                                                 │
│ hh-scout.service = aiogram bot + APScheduler + pipeline (Selenium в потоке) → SQLite data/hh_scout.db │
│        │                                              └──► hh-scout-bridge.service :8766 → claude -p   │
│        └──► Telegram (только владелец)                                                             │
└────────────────────────────────────────────────────────────────────────────────────────────────────┘
```
Один процесс Python: aiogram polling + `AsyncIOScheduler`. Пайплайн синхронный, выполняется через `asyncio.to_thread`
со своим соединением SQLite (WAL, busy_timeout 5 с). Внутри процесса сборы сериализует `asyncio.Lock`; между процессами —
только запись `runs.status='running'`: второй процесс видит её и **сразу выходит** («уже идёт другой прогон»); зависшие
записи снимаются через 3 ч. Это не защищает от CLI, запущенного, когда `runs` уже закрыт, а сессия Marionette ещё занята.

## Один прогон (`pipeline/run.py: run_crawl`)
Дневной лимит загрузок — `pipeline/budget.daily_cap`: случайное число из `DAILY_PAGE_LOADS_MIN..MAX`, тянется один раз
в день и хранится в kv `daily_cap:<дата>`; остаток = лимит − `page_loads_today` (все прогоны). Плановый подход получает
`budget` = ⌈остаток / подходов, оставшихся сегодня⌉ (считает планировщик), ручной `/crawl` и CLI — весь остаток.
Шаги изолированы: ошибка браузера
(`BrowserUnavailable`, `HHBlocked`) пропускает браузерные шаги, ошибка моста (`BridgeError`) — ИИ-шаги; остальное выполняется.

|---|---|---|---|---|

| 5c | Очередь лидов | `pipeline/repo.py` | `evaluated ≥ порога` — это **очередь, живущая дольше суток**: приоритет = балл + 1 за каждые сутки ожидания (потолок `QUEUE_WAIT_BONUS_MAX` = 7). Что не влезло в норму — не отбрасывается, ждёт и соревнуется завтра; старше `QUEUE_TTL_DAYS` (30) → `rejected/queue_expired` | — |
| 5b | Досье на компанию | `llm/company_research.py` | Перед письмом, для hh-лидов с `employer_id`: CLI с веб-инструментами читает `hh.ru/employer/<id>` и сайт компании → `employers` (1 вызов на **компанию**, кэш `COMPANY_RESEARCH_TTL_DAYS`). Сбор: задачи = `SEARCH_QUERIES` × проходы (regional: 49 регионов одним запросом; remote: `work_format=REMOTE`;
project: `employment_form=PROJECT,PART`), в случайном порядке; пагинация до `max_pages_per_query` (6) с ранней
остановкой, когда страница ≥ 2 не даёт новых. Браузерные шаги идут **сериями по времени** (`browser/bursts.py`,
политика `pacing.policy_from_settings`): подключение → листаем `BURST_MINUTES` (7–13 мин) с «чтением» 6–20 с на страницу
(каждая ~6-я 25–60 с) и прокруткой → отсоединение → тишина `GAP_MINUTES` (4–9 мин). Серия заканчивается раньше, если
кончилась работа или бюджет прогона. Между сериями Firefox свободен. Между **стадиями** одного подхода
(лента profi → сбор → описания) выдерживается такая же пауза, как между сериями (`run._rest_between_stages`, v9.11) —
без неё стык «сбор → описания» давал ~20 мин листания подряд. Окно бота ничем на странице не помечено: его хендл
лежит в kv `bot_window_handle` (`browser/session.WindowRegistry`), и прогон закрывает оставшееся от прерванного
окно по хендлу — только своё, в чужие окна сессия не заходит. Переход между страницами hh.ru делается из самой
страницы (`location.assign`), прокрутка — колесом через `ActionChains` с откатом на скрипт. Блок (`HHBlocked`)
пробрасывается из стадии в `run_crawl`: `CrawlReport.blocked`, описания после блока не открываются, тревога 🚫.
Каждая стадия пишет в `runs.page_loads` **сумму** с предыдущими (`page_loads_before`); серия, прерванная
исключением, всё равно доходит до `after_burst`.

Итог прогона — `CrawlReport.as_text()` одним сообщением владельцу; метрики в `runs`.

## Лиды-компании (v9.13, решение №53)
Единица лида — компания, вакансия лишь повод её увидеть. Три канала (`COMPANY_CHANNELS`, по умолчанию все):
- `panel` и `design` — задачи сбора по `COMPANY_QUERIES` (одна на канал, вся Россия): карточки получают
  `lead_kind='company'` (`repo.insert_card`), префильтр не требует инженерного слова, триаж идёт по
  `prompts/company_triage.md` (пачки по виду не смешиваются), страница вакансии читается как описание компании,
  оценка — `prompts/company_evaluation.md` → `CompanyEvaluation` (fit, lead, company_kind ∈ panel_builder /
  design_bureau / integrator / …, offer_focus), балл `ranker.company_total_score` = 0.6·fit + 0.4·lead.
  Стартовый проход: `python -m hh_scout.pipeline.collector --pass panel --period 30` (без синхронизации откликов).
- `owen_si` — каталог интеграторов ОВЕН (`sources/owen.py`): JSON `integrators.php` читается `httpx` с хоста
  (браузер и hh не задействованы), дилеры и скрытые записи отсеиваются, компании входят `new`; перед оценкой каждый
  прогон допускает `COMPANY_LEADS_PER_DAY` штук (`repo.admit_company_leads`, Золотой → Серебряный → остальные);
  обновление каталога — `Scheduler.owen_job` по воскресеньям 04:00 и CLI `python -m hh_scout.sources.owen [--admit N]`.
  Досье (`company_research`) для них читает страницу проектов на owen.ru и сайт компании, hh не открывает.
Дальше — общая очередь, норма, мгновенная отправка и дайджест. Письмо — `prompts/company_offer.md`
(`rows.letter_key(row) == 'company'`: свой промпт, отпечаток правил, рамка 400–3000, редактор с оговоркой про
партнёрство), карточка — `ranker.format_company_card` (канал, «Найдена по», соответствие/лид, «Предложить: …»,
контакты из каталога), в Telegram — «🤝 Предложение партнёрства». `/stats` — разрезы «Тип лида» и «Канал»; для
каталога исход `blind`. Недоступные с хоста источники (InSAT, тендеры) — в ROADMAP.

## Второй источник — profi.ru (`profi/pages.py`, `pipeline/profi_collector.py`, v7)
Заказы клиентов из кабинета специалиста (`PROFI_ORDERS_URL`, по умолчанию `profi.ru/backoffice/n.php`; нужен вход на
profi.ru в том же Firefox). Кабинет — JS-приложение без встроенного JSON, парсим DOM: карточка `<a data-testid="<id>_order-snippet">`
даёт заголовок (`aria-label`/`h3`), бюджет («до 5000 ₽»), полный текст («Пожелания и особенности: …»), формат и город
(`li[aria-label="Дистанционно:"]` → `remote`; «У клиента» → `field`; «У специалиста» → `office`), удобное время, имя клиента,
«Вчера в 12:09» → `published_at`. Строка `vacancies`: `hh_id='profi:<id>'` (глобальный `UNIQUE` сохраняется), `site='profi'`,
`employer`=имя клиента, `employment='project'`, `source=search_pass='profi'`, `raw_json={description, budget, when, client, …}`,
`salary_raw={"profi_budget": "до 5000 ₽", to, …}` (`hh/salary.human_from_raw` показывает бюджет как написано).
Дальше — общий пайплайн: оценка (`prompts/profi_order_evaluation.md`, пачки по сайтам не смешиваются, `ip_gph_possible=yes`),
предложение клиенту вместо письма (`prompts/profi_bid.md`, ориентир 400–900, код принимает 150–1500 знаков), карточка с пометкой «🛠 заказ на profi.ru»,
те же кнопки. **Доставка сразу**: `Scheduler.after_crawl` → `bot/digest.send_instant_leads(site='profi')` — карточка + предложение
сразу после прогона, запись в `digests` с `note='instant:profi'` без отсева ниже порога (это делает дневной дайджест).
`/done profi:<id>`, `/letter profi:<id>` работают; автозакрытие по откликам — только hh.ru (`applied` у заказов всегда 0).
Правила profi.ru запрещают парсинг — источник выключен по умолчанию, след минимальный (1 страница за подход, только чтение),
тревога `profi_blocked` раз в день. Снимок ленты для парсера/фикстур — `scripts/profi_snapshot.py` (читает уже открытые вкладки).

## Расписание (`scheduler.py`)
- **digest** — cron `DIGEST_TIME` (12:00): `send_digest()` (внутри — сначала `_evaluate_pending`: дооценить всё
  `prefiltered` и дописать письма на отдельном соединении, чтобы идущий или только что закончившийся подход попал в
  дайджест хотя бы частично; то же при ручном `/digest`). Сборы дайджест **не планирует**.
- **Подходы** (`CRAWL_WINDOWS`, по умолчанию 07:00–10:00, 12:00–15:00, 18:00–22:00): один плановый сбор на окно.
  `next_sitting(now, windows, done_idx_today)` — первое окно с индексом больше уже использованного сегодня, в котором
  после «сейчас + 20 мин» остаётся хотя бы `MIN_SITTING_MINUTES` (60); старт — случайная точка из
  `[начало окна, конец − 60 мин]`; иначе первое окно завтра. kv: `next_crawl_at`, `crawl_window_idx`, `crawl_window_date`
  (план) и `sitting_done` = `дата:idx` (какое окно сегодня уже использовано).
- **crawl** — одноразовый DateTrigger: при `kv.paused` — запись в журнал и сразу план следующего подхода; иначе
  `run_crawl('schedule', budget=share, deadline=sitting_deadline)`, где `share = ⌈(daily_cap − page_loads_today) / sittings_left⌉`,
  а `sitting_deadline(day, windows, idx)` = конец окна + `SITTING_GRACE_MIN` (30). Дедлайн работает через `should_stop`:
  серии `bursts.run_in_bursts` не начинаются и не уходят в паузу после него, недобор доли сгорает, оценка и письма (мост)
  выполняются; в отчёте — «остановлен по концу окна в HH:MM» (`CrawlReport.deadline_hit`). Если при старте окно уже закрылось
  (подход восстановлен после долгого простоя) — пропуск (журнал), план следующего. Перед запуском `next_crawl_at`
  очищается (индекс и дата окна остаются — рестарт посреди сбора не назначит это окно снова), после прогона — план следующего
  подхода. **Тихий режим**: плановый подход не сообщает ни о старте, ни об исходе; отчёт (`CrawlReport.as_text()` + время
  следующего подхода) уходит владельцу только если `not report.ok` и `analyze_report` не отправил ни одной тревоги — иначе
  тревога с подсказкой заменяет отчёт. Ручной `/crawl [N]` план не трогает, берёт весь остаток лимита (N ограничивает
  страницы), получает дедлайн `now + MANUAL_SITTING_MINUTES` (90) и отвечает всегда: «▶️ Начинаю сбор…» (с предупреждением,
  если сейчас не окно) и отчёт. Плановый подход, совпавший с ручным, отмечает своё окно и планирует следующее, а не
  исчезает. Ошибка браузера: ретраев нет — следующий подход через несколько часов, владельцу тревога 🦊 про `--marionette`.
- Старт сервиса (`_restore_crawl`): `next_crawl_at` в будущем → тот же job, **но** план на другой день при свободном
  окне сегодня (нет `sitting_done` за это окно, до конца окна > 20 мин) заменяется подходом сегодня; в прошлом →
  дедлайн считается от **запланированного** дня (`crawl_window_date`): окно ещё открыто — подход через 2–5 мин, окно
  закрылось (вчерашний вечер, рестарт ночью) — подход потерян, планируется следующий (решение №17, v9.11: раньше
  сервис листал hh.ru в 02:00). Плановые прогоны в статусе `running` при старте помечаются прерванными сразу — они живут
  только внутри процесса сервиса. Ключа нет → `plan_next_crawl()` сразу (первая установка, рестарт посреди сбора).
- Любая ошибка job'а → одна строка владельцу, traceback в журнал.

## Что ответили компании (`pipeline/outcomes.py`, v9.7)
Синхронизация откликов пишет не только «работодатель что-то ответил» (`has_chat`), но и состояние переписки с hh
(`negotiation_state`: RESPONSE / INTERVIEW / DISCARD). Успех метода — `INTERVIEW`, отказ — неудача (решение №42).
Синхронизация (`pipeline/negotiations.py`, общая для подхода и для `scripts/sync_negotiations.py`) читает
`NEGOTIATIONS_PAGES` страниц списка (по 20 записей) — по одной за вызов `step()`, с выходом при пустой странице,
при повторе id и по `paging`; каждая смена состояния пишется в `negotiation_events`.
Аналитика — `pipeline/outcomes.py`: `outcome_of` (invited / refused / answered / silent / blind), `outcome_stats` по
полосам `SCORE_BANDS`, `outcome_by` по признакам из `DIMENSIONS`, `maturing`, `reply_delay_curve`. **Обе** таблицы
`/stats` считаются по одной выборке (`repo.outcome_rows`), по одной зрелости `OUTCOME_MATURE_DAYS` и с одним
значением «ответ = написали и не отказали» (приглашения отдельно; доля — ответы и приглашения вместе); долю в ячейках
меньше `MIN_CELL` заменяет «мало данных» (решения №48, №49). Возраст письма — от первой доставки (`digests.sent_at`).
`evaluator.feedback_block` подмешивает исход к каждому 👍/👎 через `outcomes.outcome_note` — с той же зрелостью,
так что свежее письмо не называется «молчит», — а причина 👎 печатается кодом или словами владельца.
Письма мимо hh.ru (`applied = 0`) идут отдельной строкой «без канала измерения».
Сколько суток компания ищет на ту же роль — `repo.employer_searching_days` по нашей же истории (hh обновляет дату
публикации при каждом поднятии, поэтому возраст вакансии бесполезен); от 14 суток карточка помечается «🔁 ищут N дн.».

## Резервная копия БД (v9.7, этап 7)
`Scheduler.backup_job` в 03:30 зовёт `db.backup` (штатный SQLite backup API — безопасно на ходу), кладёт
`data/backups/hh_scout-<дата>.db`, держит 7 копий, пишет kv `last_backup`; дата видна в `/status`, сбой — тревога.

## Мгновенная доставка лидов (v9.8)
`Scheduler.after_crawl` → `bot/digest.send_instant_leads` для `hh`, затем для `profi` (если включён): лид, у которого
письмо уже написано (`run.py` шаг 6), уходит владельцу **сразу после подхода**, а не ждёт полудня. Из очереди
`repo.lead_queue` берутся лиды с годным письмом в пределах остатка суточной нормы (`DIGEST_MAX_ITEMS` −
`repo.leads_sent_today`). Лид без письма (мост подвёл) остаётся в очереди — минуты обращений к мосту не держат чат;
так же придерживается лид, чьё письмо написано по прежним правилам (`usable_letter`, отпечаток — по сайту строки):
его перепишет ближайший подход или дооценка перед дайджестом. Дайджест и мгновенные отправки идут под одним
`asyncio.Lock` (`main.py`), а общий цикл доставки — `bot/digest._deliver`. Запись — `digests` с `note='instant:<site>'`
и `reject=False`: чистку того, что ниже порога, по-прежнему делает дайджест 12:00.
Норма — свойство суток, а не сообщения: `plan_digest` в 12:00 берёт **остаток** нормы, поэтому второй порции не будет,
а шапка вместо «лидов не нашлось» говорит, сколько уже ушло сразу. «Проверено N» в дневной шапке считается от
предыдущего **полуденного** дайджеста (`evaluations_since_last_digest(daily_only=True)`), а не от последней отправки.

## Тревоги (`health.py`)
Урок 09.09: сервис весь день молчал, потому что сообщал только об исходе сбора, а не о его отсутствии. Теперь:
- **Сторож** (`Scheduler.watchdog_job`, каждые 30 мин): окно закрылось (+30 мин) без стартовавшего прогона → «⚠️ Окно … прошло
  без подхода»; нет `next_crawl_at` и сбор не идёт → тревога и `plan_next_crawl()` сразу; после последнего окна 0 загрузок за
  день → «🚨»; запись `runs.status='running'` старше 3 ч при свободном `crawl_lock` → «висит». После последнего окна, когда сбор
  не идёт — `day_summary_alert`: «⚠️ Итог дня: подходов k из n · страниц U/CAP · новых · лидов» **только при недоборе
  подходов**; полный день помечается в kv (`Alerter.mark_sent`) и не сообщается — о сделанной работе говорит строка
  «Работа за сутки» в дайджесте 12:00. На паузе сторож молчит.
- **Предпроверка** (`precheck_job`, за 30 мин до подхода): порт Marionette и `GET /health` моста; недоступны → предупреждение
  до срыва.
- **Разбор отчёта** (`health.analyze_report` после каждого прогона): капча/вход (`HHBlocked`), браузер недоступен, hh.ru не видит
  соискателя, поиск без карточек, ≥3 страниц вакансий без `vacancyView` и не меньше половины, мост недоступен — каждая со своей
  подсказкой.
- **Дедупликация**: `health.Alerter` шлёт ключ один раз в день (kv `alert:<key>:<дата>`), старые ключи чистятся; `/status`
  показывает время последней проверки и число тревог за день.
- **Падение процесса** — вне Python: `Restart=on-failure` перезапускает бота (молча, только журнал); 5 падений за 10 мин →
  unit `failed` → `OnFailure=hh-scout-alert.service` → `scripts/tg_alert.sh` шлёт «🚨» через curl.

## Дайджест (`pipeline/digest_builder.py`, `bot/digest.py`)
остаток суточной нормы (`DIGEST_MAX_ITEMS` 20 минус уже отправленное сегодня) по приоритету очереди; лишние остаются `evaluated`
до следующего раза. Письма (недостающие и устаревшие) пишет **только** дооценка перед дайджестом (`_evaluate_pending`,
своё соединение); пока идёт подход, дооценка пропускается — подход пришлёт лиды сам. Лид без годного письма уходит
карточкой без письма. Сообщения: заголовок «Лиды за <дата> — N
(проверено M вакансий)» (+ строка «Необработанных с прошлых дней: K (/inbox)», если K > 0) → на каждый лид карточка (`ranker.format_card`, клавиатура из двух рядов — см. ниже) + письмо (`format_letter`, `<pre>`),
пауза 1.0 с. Затем `sent` + `digests/digest_items`; всё `evaluated` ниже порога → `rejected` (кроме строк с
`evaluations.floor = 1`). **Дневной минимум** (v9.12, решение №52): первым шагом `digest_builder.promote_floor` считает,
сколько лидов ушло за последние 24 ч (`repo.leads_sent_since`); если меньше `DAILY_LETTERS_FLOOR` (5) — берёт из
`repo.floor_candidates` лучшие hh-вакансии ниже порога (`evaluated`, или `rejected` по баллу не старше
`FLOOR_LOOKBACK_DAYS`; балл ≥ `FLOOR_MIN_TOTAL`, роль ≥ `FLOOR_MIN_ROLE`, не агентство, компания не отвечена и без лида,
одна на компанию), ставит им `floor = 1` и возвращает в очередь; дооценка тем же проходом пишет им письма, карточка
получает строку «📉 Ниже порога, взят по дневному минимуму», шапка — «Добрано по дневному минимуму: N».
Пусто → «Сегодня лидов не нашлось.
Проверено M новых вакансий.» M = число оценок с прошлого дайджеста. При первом старте сервиса уже показанные превью
помечаются `sent` без отправки (`kv.preview_marked`). `plan_digest` перед выборкой ещё раз вызывает `dedup.dedupe_evaluated` (страховка: лид мог быть отправлен вчера, двойник оценён сегодня).

## Жизненный цикл лида в чате (`bot/feedback.py`, `bot/lead_actions.py`)
Под карточкой два ряда кнопок: `[👍] [👎]` и `[✅ Написал] [⏸ Позже]`. Лид **открыт**, пока `status='sent'` и в
`lead_actions` нет закрывающего действия (`responded`, `auto_responded`, `disliked`, `closed_stale`).
- 👍 → `feedback(+1)` + `liked`, карточка остаётся открытой (кнопка «👍 отмечено»).
- 👎 → клавиатура причин (💰 зарплата · 🏢 формат · 🔧 не мой стек · 🏷 агентство · ✍️ своими словами · пропустить) →
  `feedback(−1, reason)` + `disliked` → карточка **сворачивается** в строку «👎 Мимо дд.мм · причина · Компания · Название»,
  письмо удаляется. «✍️ своими словами» (v9.11): бот просит причину ответом на своё сообщение (kv `awaiting_reason`),
  текст ответа (до 300 знаков) ложится в `feedback.reason` и в свёрнутую строку и попадает в калибровочный блок
  оценщика дословно.
- `/letter <id>` по лиду из очереди: карточка + письмо, лид становится `sent` (`digests.note='manual:/letter'`) —
  дальше как обычный лид.
- ✅ Написал → `feedback(+1)` + `responded` → «✅ Написал дд.мм · …», письмо удаляется.
- ⏸ Позже → `deferred`, карточка открыта, в `/inbox` внизу.
- После каждого сбора: лиды, на которые владелец откликнулся на hh.ru сам (`applied=1`), сворачиваются автоматически
  как `auto_responded` («✅ Откликнулся на hh.ru · …») — `lead_actions.collapse_auto_responded` из `Scheduler.after_crawl`.
- `/inbox` — открытые лиды (старые сначала, отложенные внизу); `/done <hh_id>` — как ✅ (тоже пишет `feedback(+1)`);
  `/cleanup [дней=14]` — открытые старше N дней → `closed_stale` («⌛ Устарело»). Автоматического устаревания нет.
- Callback-протокол: `fb:<id>:up|down`, `fbr:<id>:<reason|skip>`, `act:<id>:responded|later`, `noop`. Подписи кнопок
  меняются на месте: «👍 отмечено», «⏸ отложено». `liked`/`deferred` пишутся один раз, `feedback` — при каждом нажатии.
  Сворачивание правит карточку и письмо **последнего** дайджеста этого лида; для закрытого/не отправленного лида —
  ответ «Лид уже закрыт» и замороженная клавиатура. Уведомления: «✅ Свернул N лид(ов)…», «⚠️ Автозакрытие лидов не выполнено».
Сворачивание = `edit_message_text` карточки без клавиатуры + `delete_message` письма (`digest_items.letter_message_id`);
ошибки Telegram логируются, не падают. `evaluator.feedback_block` подмешивает до 20 последних записей `feedback`
(с пометкой, если кандидат написал компании). Дообучения нет.

## Команды бота (только `TG_OWNER_CHAT_ID`; чужие апдейты игнорируются, в лог — INFO)
`/start` `/help` — справка · `/status` — Firefox, мост, автосбор/пауза, идёт ли сбор, следующий подход (окно i из n),
загрузок сегодня / лимит дня, очередь описаний, последний прогон, счётчики статусов, сторож (последняя проверка, тревог
сегодня), размер БД · `/digest` — дооценить загруженное (вызовы моста) и прислать лиды сейчас ·

`/next` — время следующего сбора · `/pause` `/resume` · `/skipped [N≤50]` — последние отсеянные · `/letter <hh_id>` —
переписать письмо и прислать карточку с письмом · `/inbox` — открытые лиды · `/done <hh_id>` — отметить «написал» ·
`/cleanup [дней]` — свернуть устаревшие · `/stats [дней]` — исходы по полосам балла.
