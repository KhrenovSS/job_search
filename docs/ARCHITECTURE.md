# Архитектура HH-Scout

## Компоненты
```
┌──────────────────────────── Debian-хост, X11-сессия владельца (24/7) ────────────────────────────┐
│ Firefox ESR --marionette (127.0.0.1:2828, логин владельца на hh.ru)                              │
│        ▲ Marionette (одна сессия!)                                                                │
│ geckodriver --connect-existing  ← дочерний процесс на время серии, потом убивается (без quit())    │
│        ▲ WebDriver                                                                                 │
│ hh-scout.service = aiogram bot + APScheduler + pipeline (Selenium в потоке) → SQLite data/hh_scout.db │
│        │                                              └──► hh-scout-bridge.service :8766 → claude -p   │
│        └──► Telegram (только владелец)                                                             │
└────────────────────────────────────────────────────────────────────────────────────────────────────┘
```
Один процесс Python: aiogram polling + `AsyncIOScheduler`. Пайплайн синхронный, выполняется через `asyncio.to_thread`
со своим соединением SQLite (WAL, busy_timeout 5 с). Внутри процесса сборы сериализует `asyncio.Lock`; между процессами —
только запись `runs.status='running'`: второй процесс видит её и **сразу выходит** («уже идёт другой прогон»); зависшие
записи снимаются через 3 ч. Это не защищает от CLI, запущенного, когда `runs` уже закрыт, а сессия Marionette ещё занята.

## Один прогон (`pipeline/run.py: run_crawl`)
Дневной лимит загрузок — `pipeline/budget.daily_cap`: случайное число из `DAILY_PAGE_LOADS_MIN..MAX`, тянется один раз
в день и хранится в kv `daily_cap:<дата>`; остаток = лимит − `page_loads_today` (все прогоны). Плановый подход получает
`budget` = ⌈остаток / подходов, оставшихся сегодня⌉ (считает планировщик), ручной `/crawl` и CLI — весь остаток.
Шаги изолированы: ошибка браузера
(`BrowserUnavailable`, `HHBlocked`) пропускает браузерные шаги, ошибка моста (`BridgeError`) — ИИ-шаги; остальное выполняется.

| # | Шаг | Модуль | Вход → выход | Ресурс |
|---|---|---|---|---|
| 1 | Сбор | `pipeline/collector.py` | страницы поиска → `vacancies(new)`; страница откликов → `applied/has_chat` (+`suitableVacancies` как проход `similar`) | браузер |
| 2 | Правила | `pipeline/prefilter.py` | `new → triage` или `skipped` (applied, archived, fly_in_fly_out, stopword, no_engineering_title) | — |
| 3 | Триаж ИИ | `llm/triage.py` | карточки пачками по 30 → `to_fetch` (+priority 1–3) или `skipped/triage` | мост |
| 4 | Описания | `pipeline/details.py` | сначала `repo.expire_low_priority`: `to_fetch` с приоритетом 3 старше `LOW_PRIORITY_TTL_DAYS` (3) → `skipped/low_priority_expired`; затем `to_fetch` по приоритету → страница вакансии → `prefiltered` (архив/отклик → `skipped`; страница без `vacancyView` → `evaluation_failed`) | браузер, остаток бюджета прогона |
| 5 | Оценка | `llm/evaluator.py` | `prefiltered` пачками по 5 → `evaluations` (tech/role/lead, verdict, pitch_hint…) → `evaluated`; total = код | мост |
| 6 | Письма | `llm/cover_letter.py` | `evaluated` с `total ≥ порог` без письма → `cover_letters` (1 вызов на лид) | мост |

Сбор: задачи = `SEARCH_QUERIES` × проходы (regional: 49 регионов одним запросом; remote: `work_format=REMOTE`;
project: `employment_form=PROJECT,PART`), в случайном порядке; пагинация до `max_pages_per_query` (6) с ранней
остановкой, когда страница ≥ 2 не даёт новых. Браузерные шаги идут **сериями по времени** (`browser/bursts.py`,
политика `pacing.policy_from_settings`): подключение → листаем `BURST_MINUTES` (7–13 мин) с «чтением» 6–20 с на страницу
(каждая ~6-я 25–60 с) и прокруткой → отсоединение → тишина `GAP_MINUTES` (4–9 мин). Серия заканчивается раньше, если
кончилась работа или бюджет прогона. Между сериями Firefox свободен. Окно бота помечено `window.name=hh-scout-bot` и закрывается при следующем подключении, если осталось.

Итог прогона — `CrawlReport.as_text()` одним сообщением владельцу; метрики в `runs`.

## Расписание (`scheduler.py`)
- **digest** — cron `DIGEST_TIME` (12:00): `send_digest()` (внутри — сначала `_evaluate_pending`: дооценить всё
  `prefiltered` и дописать письма на отдельном соединении, чтобы идущий или только что закончившийся подход попал в
  дайджест хотя бы частично; то же при ручном `/digest`). Сборы дайджест **не планирует**.
- **Подходы** (`CRAWL_WINDOWS`, по умолчанию 07:00–10:00, 12:00–15:00, 18:00–22:00): один плановый сбор на окно.
  `next_sitting(now, windows, done_idx_today)` — первое окно с индексом больше уже использованного сегодня, в котором
  ещё есть место после «сейчас + 20 мин»; старт — случайная точка внутри; иначе первое окно завтра. kv: `next_crawl_at`,
  `crawl_window_idx`, `crawl_window_date` (план) и `sitting_done` = `дата:idx` (какое окно сегодня уже использовано).
- **crawl** — одноразовый DateTrigger: при `kv.paused` — уведомление и сразу план следующего подхода; иначе
  `run_crawl('schedule', budget=share)`, где `share = ⌈(daily_cap − page_loads_today) / sittings_left⌉`; перед запуском
  `next_crawl_at` очищается (индекс и дата окна остаются — рестарт посреди сбора не назначит это окно снова), после
  прогона — план следующего подхода и отчёт с его временем. Ручной `/crawl [N]` план не трогает; N ограничивает страницы. Ошибка браузера: ретраев нет — следующий подход через
  несколько часов, владельцу напоминание про `--marionette`. Ручной `/crawl` план не трогает и берёт весь остаток лимита.
- Старт сервиса (`_restore_crawl`): `next_crawl_at` в будущем → тот же job, **но** план на другой день при свободном
  окне сегодня (нет `sitting_done` за это окно, до конца окна > 20 мин) заменяется подходом сегодня; в прошлом → через
  2–5 мин (перенесённый вчерашний подход не помечает сегодняшнее окно использованным); ключа нет → `plan_next_crawl()`
  сразу (первая установка, рестарт посреди сбора). План из v5 (без индекса окна) дополняется индексом по времени.
- Любая ошибка job'а → одна строка владельцу, traceback в журнал.

## Тревоги (`health.py`)
Урок 09.09: сервис весь день молчал, потому что сообщал только об исходе сбора, а не о его отсутствии. Теперь:
- **Сторож** (`Scheduler.watchdog_job`, каждые 30 мин): окно закрылось (+30 мин) без стартовавшего прогона → «⚠️ Окно … прошло
  без подхода»; нет `next_crawl_at` и сбор не идёт → тревога и `plan_next_crawl()` сразу; после последнего окна 0 загрузок за
  день → «🚨»; запись `runs.status='running'` старше 3 ч при свободном `crawl_lock` → «висит». После последнего окна, когда сбор
  не идёт — «📊/⚠️ Итог дня: подходов k из n · страниц U/CAP · новых · лидов». На паузе сторож молчит.
- **Предпроверка** (`precheck_job`, за 30 мин до подхода): порт Marionette и `GET /health` моста; недоступны → предупреждение
  до срыва.
- **Разбор отчёта** (`health.analyze_report` после каждого прогона): капча/вход (`HHBlocked`), браузер недоступен, hh.ru не видит
  соискателя, поиск без карточек, ≥3 страниц вакансий без `vacancyView` и не меньше половины, мост недоступен — каждая со своей
  подсказкой.
- **Дедупликация**: `health.Alerter` шлёт ключ один раз в день (kv `alert:<key>:<дата>`), старые ключи чистятся; `/status`
  показывает время последней проверки и число тревог за день.
- **Падение процесса** — вне Python: `Restart=on-failure` перезапускает бота (он сам пишет «🟢 запущен»); 5 падений за 10 мин →
  unit `failed` → `OnFailure=hh-scout-alert.service` → `scripts/tg_alert.sh` шлёт «🚨» через curl.

## Дайджест (`pipeline/digest_builder.py`, `bot/digest.py`)
`evaluated` с `total ≥ score_threshold` по убыванию total, не больше `DIGEST_MAX_ITEMS` (20); лишние остаются `evaluated`
до следующего раза. Лидам без письма письмо дописывается перед отправкой. Сообщения: заголовок «Лиды за <дата> — N
(проверено M вакансий)» (+ строка «Необработанных с прошлых дней: K (/inbox)», если K > 0) → на каждый лид карточка (`ranker.format_card`, клавиатура из двух рядов — см. ниже) + письмо (`format_letter`, `<pre>`),
пауза 0.6 с. Затем `sent` + `digests/digest_items`; всё `evaluated` ниже порога → `rejected`. Пусто → «Сегодня лидов не нашлось.
Проверено M новых вакансий.» M = число оценок с прошлого дайджеста. При первом старте сервиса уже показанные превью
помечаются `sent` без отправки (`kv.preview_marked`).

## Жизненный цикл лида в чате (`bot/feedback.py`, `bot/lead_actions.py`)
Под карточкой два ряда кнопок: `[👍] [👎]` и `[✅ Написал] [⏸ Позже]`. Лид **открыт**, пока `status='sent'` и в
`lead_actions` нет закрывающего действия (`responded`, `auto_responded`, `disliked`, `closed_stale`).
- 👍 → `feedback(+1)` + `liked`, карточка остаётся открытой (кнопка «👍 отмечено»).
- 👎 → клавиатура причин (💰 зарплата · 🏢 формат · 🔧 не мой стек · 🏷 агентство · пропустить) → `feedback(−1, reason)` +
  `disliked` → карточка **сворачивается** в строку «👎 Мимо дд.мм · причина · Компания · Название», письмо удаляется.
- ✅ Написал → `feedback(+1)` + `responded` → «✅ Написал дд.мм · …», письмо удаляется.
- ⏸ Позже → `deferred`, карточка открыта, в `/inbox` внизу.
- После каждого сбора: лиды, на которые владелец откликнулся на hh.ru сам (`applied=1`), сворачиваются автоматически
  как `auto_responded` («✅ Откликнулся на hh.ru · …») — `lead_actions.collapse_auto_responded` из `Scheduler.after_crawl`.
- `/inbox` — открытые лиды (старые сначала, отложенные внизу); `/done <hh_id>` — как ✅ (тоже пишет `feedback(+1)`);
  `/cleanup [дней=14]` — открытые старше N дней → `closed_stale` («⌛ Устарело»). Автоматического устаревания нет.
- Callback-протокол: `fb:<id>:up|down`, `fbr:<id>:<reason|skip>`, `act:<id>:responded|later`, `noop`. Подписи кнопок
  меняются на месте: «👍 отмечено», «⏸ отложено». `liked`/`deferred` пишутся один раз, `feedback` — при каждом нажатии.
  Сворачивание правит карточку и письмо **последнего** дайджеста этого лида; для закрытого/не отправленного лида —
  ответ «Лид уже закрыт» и замороженная клавиатура. Уведомления: «✅ Свернул N лид(ов)…», «⚠️ Автозакрытие лидов не выполнено».
Сворачивание = `edit_message_text` карточки без клавиатуры + `delete_message` письма (`digest_items.letter_message_id`);
ошибки Telegram логируются, не падают. `evaluator.feedback_block` подмешивает до 20 последних записей `feedback`
(с пометкой, если кандидат написал компании). Дообучения нет.

## Команды бота (только `TG_OWNER_CHAT_ID`; чужие апдейты игнорируются, в лог — INFO)
`/start` `/help` — справка · `/status` — Firefox, мост, автосбор/пауза, идёт ли сбор, следующий сбор, загрузок сегодня,
последний прогон, счётчики статусов, размер БД · `/digest` — дооценить загруженное (вызовы моста) и прислать лиды сейчас ·
`/crawl` — прогон сейчас ·
`/next` — время следующего сбора · `/pause` `/resume` · `/skipped [N≤50]` — последние отсеянные · `/letter <hh_id>` —
переписать письмо и прислать карточку с письмом · `/inbox` — открытые лиды · `/done <hh_id>` — отметить «написал» ·
`/cleanup [дней]` — свернуть устаревшие.
